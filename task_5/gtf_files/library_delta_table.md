# Library Delta Table — Reconciling Source A vs Source B

This table reconciles the conflicting claims in `capability_notes_source_a.md` and
`capability_notes_source_b.md` against what `agent_spatial_benchmark_run1.csv` and
`agent_spatial_benchmark_run2.csv` actually show (see `benchmark_comparison_annotated.png`).

Each benchmark file logs 6 individual trials per stack per run (24 rows each); all figures
below are the per-stack mean across those 6 trials, not a single reading, so the divergences
called out here reflect a consistent pattern across repeated trials rather than one-off noise.

| # | Conflict | Source A says | Source B says | What the benchmark shows | Reconciliation |
|---|---|---|---|---|---|
| 1 | Does `roughjs` expose bounding-box metadata natively? | Yes — bounding box is readable directly off the rendered element, no extra tooling needed. | No — `roughjs` only draws; a custom serializer is required to capture geometry as structured metadata. | Stack S1 (`react-flow + roughjs + dagre`, no `elkjs`, no serializer-equivalent layer) swings from 58.0% to 41.0% spatial accuracy between runs, a 17-point gap, the largest divergence in the whole dataset. Every stack that adds `elkjs` (S2, S4) stays under 5 points across runs. | The instability is only present when nothing besides `roughjs`/`dagre` is doing layout bookkeeping. That pattern matches Source B: if `roughjs` reliably exposed bounding boxes on its own, spatial accuracy should be stable run-to-run regardless of what else is in the stack, not swing by 17 points. **Source B's account is better supported by the evidence.** |
| 2 | Is `dagre` alone sufficient for dependency resolution? | Yes — `dagre`'s graph object fully covers predecessor/successor traversal. | Implied no above ~40 nodes, but not directly about dependency resolution itself. | `dep_resolution_hit_rate_pct` is the most stable metric across all four stacks in both runs (deltas under 3 points everywhere, including S1 with no `elkjs`). | Dependency resolution itself does **not** show the instability seen elsewhere. **Source A's claim that `dagre` is sufficient for dependency traversal is supported** — this part of Source A's notes holds up even though its `roughjs` claim doesn't. |
| 3 | Is `elkjs` required? | No — recommend against it; adds bundle size/complexity without payoff. | Yes — required for multi-page graphs, especially page-level layout consistency. | The two stacks that include `elkjs` (S2, S4) are the most run-to-run stable across every metric, and S3 (`+d3-hierarchy`, no `elkjs`) shows the single worst divergence in the dataset: page-navigation success drops from 88.0% to 66.0%, a 22-point swing. Latency moves the other way: adding `elkjs` costs roughly 190 ms on the base stack (S1 ~420 ms → S2 ~610 ms) and ~235 ms alongside `d3-hierarchy` (S3 ~455 ms → S4 ~690 ms), consistent to within 8 ms across both runs. | Both sources are partly right, on different axes. Source A's cost objection is real and measurable — `elkjs` is the single largest latency addition in the set, and the benchmark confirms rather than refutes that. But cost was A's only stated ground for recommending against it, and on the reliability question A is not supported: adding `d3-hierarchy` without `elkjs` does not fix page-navigation reliability, and S3 is in fact the least stable stack on that metric. Run-to-run stability only appears once `elkjs` is present. **Source B's claim that `elkjs` is needed is supported; Source A's cost concern is validated but does not outweigh it**, given that an unstable spatial or page-nav signal makes autonomous operation unreliable at any latency. One part of Source B's claim cannot be tested here — the specific "~40 nodes across pages" threshold — because the benchmark files carry no node-count column. |
| 4 | Is `d3-hierarchy` needed for page/content-position context? | Not addressed. | Yes — recommended for letting the agent know which page/parent container a node belongs to. | S4 (`elkjs + d3-hierarchy` together) is the best-performing and most stable stack overall (spatial accuracy ~82%, page nav ~90%, every percentage metric diverging under 3 points between runs). S3 (`d3-hierarchy` alone, no `elkjs`) does not show this benefit — it has the worst page-nav divergence in the set. | `d3-hierarchy`'s benefit for page context only shows up when paired with `elkjs`; on its own it does not stabilize page navigation. **Source B's recommendation to add `d3-hierarchy` is supported, but only as a complement to `elkjs`, not as a standalone fix.** |

## Net read
- Source A is right about `dagre` handling dependency resolution.
- Source A is not supported on `roughjs` bounding-box exposure. Its cost objection to `elkjs` is validated by the latency data but is outweighed by the stability evidence.
- Source B is supported on both the `roughjs` limitation and the need for `elkjs`.
- `d3-hierarchy` adds value, but only once `elkjs` is already in place — it is not a substitute for it.
