## 1. Overview

Orangutan Encyclopedia is a Computer Use Agent (CUA) benchmark project for training frontier AI models on real-world desktop and browser automation tasks.

These guidelines outline the task creation flow. Your task is to create high-quality, verifiable tasks across numerous professional domains.

The AI model will solve the prompt and create its output file, which will then be scored against a rubric based on your Ground Truth Files (GTF). The goal is to achieve model failure.

### 1.1 Glossary


| Term                           | Definition                                                                                                                                                                     |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GTF / ground truth file        | The output file created by contributors                                                                                                                                        |
| Expected file                  | The output file created by contributors. Use 'expected file' in the rubrics instead of 'GTF/ground truth file'.                                                                |
| Initial Output files           | Pre-seeded output file in prefilled tasks. Previously referred to as 'gold files'.                                                                                             |
| Virtual Machine (VM)           | A computer running inside another computer. It gives you a separate environment where you can safely open, edit, and save files without affecting your own system.             |
| Graphical User Interface (GUI) | A visual way to interact with a computer or device. Instead of typing text commands, a GUI lets you control the device by clicking or tapping on pictures, icons, and buttons. |




### 1.2 Task workflow overview

You will encounter 2 types of tasks:

1. empty tasks to start from scratch; or
2. prefilled tasks with a prompt + input files
  a. You may edit/replace the input files
   b. You may change the number and/or format of the initial output files pre-seeded with the task.

The only difference is that blank tasks have an extra sourcing step to find input files. The rest of the steps are the same for all tasks.

**[Flowchart diagram]** — visual workflow showing:

- "Task from scratch" → Source + Upload initial files
- "Task with prefilled prompt + input files" → (You may edit/replace input files & change the number and/or format of the gold files)
- Both paths converge into: **Fix/Create prompt with GUI integration**
  - Create or edit the prompt to integrate GUI interaction.
  - Specify output file names, including the file extension
  - Add instructions to save the files to the desktop
  - The goal is to create a natural, complex, and unambiguous prompt.
  - ❌ Avoid PII and time-sensitive info in the prompt
- → **Skip Asset Step** (upload later) / **Skip Rubric Step** (come back after Computer Use step)
- → **Computer Use Step (initializer + create output files)**: Paste/Replace input file URLs into the initializer and click "Execute Task Initializer": This will automatically load the 'input files' into the VM.
  - Create/Edit GTF files based on the prompt in the VM.
  - Save the GTF files to your local machine when done and upload the files to the Asset Section.
- → **Asset Upload**
  - Upload the GTF files created in the VM.
  - Make sure the filename matches the ones specified in the prompt.
- → **Create Rubric (LLM generated)**: Check rubric accuracy & completeness and make necessary edits
- → **Computer Use Section (verifier)**:
  - Copy the GTF file URL and filenames from the asset section and paste them into the verifier.
  - The uploaded filename in the asset upload and the filename in the verifier must match.

## 2. Prompt section

*For Full Domain and Application Specific Prompt Guidance, See the Prompt Writing Handbook*

### Purpose of this section

A strong prompt gives the agent one clear interpretation of the task. It explains what to produce, which files to use, where to save the output, and what success looks like without sounding like a grading rubric. The final prompt should feel like a real workplace request while still being specific enough to support reliable GTF files, rubrics, and verification.

This section is organized into three main parts:

1. Review the task context and/or source input files.
2. Rewrite/Create the prompt.
3. Validate and finalize the prompt.

> ☣️ **Caution for the Healthcare and Biology domains** ☣️
>
> Avoid prompts that deal with topics like influenza, COVID, Hantavirus, and other highly contagious pathogens of that nature - the agent will refuse to run this due to internal guardrails dealing with biorisk. It doesn't matter if the prompt's context is entirely innocent!



### 2.1 Review the Task Context (for prefilled tasks)

Before editing the prompt, understand what the task is supposed to test and what materials the agent will have available. Do not assume the seeded prompt or initial output files are already correct.


| Item to review                | What to check                                                                                      | What to do if there is an issue                                                                                |
| ----------------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Assigned domain and subdomain | Confirm that the prompt matches the domain shown in the goal section.                              | If the prompt/input files clearly belong to a different domain, replace them.                                  |
| Primary prompt                | Focus on the prompt shown on the left side of the task page.                                       | Edit this prompt when it is unclear, unnatural, too easy, or misaligned with the files. Also add GUI requests. |
| Starting files                | Confirm that the input files are usable, supported, stable, and sufficient for the requested task. | If the source files contain PII, are corrupted, unsupported, or insufficient, edit and/or replace them.        |
| Initial output files          | Compare the Initial output files against the prompt and input files.                               | Correct/Replace the Initial output files if they do not fully satisfy the final prompt.                        |
| Rubrics and verifier          | Check whether the scoring criteria can evaluate the final deliverable.                             | Update rubrics after prompt changes so they match the final task.                                              |


> **Important**
>
> The prompt on the left is the one that matters. The prompt on the right is usually a seed or duplicate and can normally be ignored. You can also ignore fields such as "CDS starting file URL to use in the initializer config JSON" and "Verifier template" unless you are troubleshooting a technical issue.

#### Initial File Check

**Input file requirements:**

- Minimum of 3 input files required
  - ❌ Input files cannot all be CSV or XLSX file inputs.
- Publicly accessible (no paywalls).
- Open source CC compliant (free for use, fully public license - NO ATTRIBUTION).
- In English.
- Less than 30MB total.
- Relevant to the chosen domain of your task.
- Avoid PII.
- Stable source: All tasks must be based on historical or static data. Verify that the data source will not change.

⛔ **Examples of unstable data sources — REPLACE the files:**

- Live stock prices or financial tickers.
- Real-time sports scores.
- Current weather data.
- Live inventory or pricing pages.
- Any page that auto-refreshes or shows 'as of today' figures.

✅ **Examples of stable data sources — ACCEPTABLE:**

- Historical quarterly revenue reports
- Wikipedia tables for completed events
- Government datasets with fixed publication dates
- Company filings (10-K, 10-Q) with specific period dates
- Archived reports/papers
- Note: Try to opt out of or modify the arXiv prompt for historic/archived papers. When working with the arXiv ID, it is possible to retrieve the paper version through the submission history; if this field does not appear, it means it is v1. There are a few ways to use it: the first is `https://arxiv.org/abs/{arxivID}v1` to fetch the version, or you can enter `{arxivID}v1` directly into the search engine to access the versioned page.

**Acceptable input file formats:**

*If you have questions on your file format reach out to the QMs*

`.pdf`, `.xlsx`, `.csv`, `.pptx`, `.docx`, `.zip`, `.jpeg`, `.png`, `.txt`, `.blend` are some of the examples for most of the tasks. If an app requires another use that can also be acceptable

### 2.3 Rewrite the Prompt

Create/Revise the prompt so it reads like a realistic workplace request while remaining specific, feasible, and verifiable. The goal is not to make the prompt longer. The goal is to make it clearer, more natural, and harder in meaningful ways.

#### A. Required prompt details

Every final prompt must include the following information in natural language:

☐ The exact GTF filename or filenames, including the correct extension.
☐ The instruction that all output files must be saved on the Desktop.
☐ The expected deliverable type, `.docx` `.pptx` `.pdf` `.zip` `.blend` `.tscn` `.escn` `.tres` `.godot` `.gd` `.scn` `.res`. etc.
☐ The core work the agent needs to complete: analysis, editing, formatting, transformation, research, correction, or creation.
☐ Any essential constraints needed to make the task unambiguous and verifiable.

**Example of a natural requirement**

> "I'm working on a presentation for work. Can you review the attached quarterly sales workbook and prepare a leadership-ready summary. Add a chart showing regional revenue by quarter, clean up the print layout so it fits on one page, and save the completed file as `regional_sales_summary.xlsx` on the Desktop."



#### B. Prompt quality standards


| Standard       | What it means                                                                                                                |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Clear          | A reasonable agent or attempter should not be able to interpret the task in multiple valid ways.                             |
| Natural        | The prompt should sound like a real request from a manager, client, teammate, or stakeholder.                                |
| Complex enough | The task should require meaningful professional judgment, multi-step execution, careful formatting, or cross-file reasoning. |
| Feasible       | The task must be possible in the Ubuntu VM using the provided files and supported tools.                                     |
| Verifiable     | The output must be something the rubric and verifier can compare against the ground truth.                                   |
| Aligned        | The prompt, GTF files, rubrics, and verifier must describe the same final task.                                              |




#### C. What to avoid


| Avoid                                     | Why it hurts quality                                                                                                                                                                           | Better approach                                                                                         |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Rubric-style language                     | It makes the prompt sound like evaluation instructions instead of a real request.                                                                                                              | Write as a natural delegation of work.                                                                  |
| Over-prescribed algorithms                | It turns the task into mechanical rule-following and often reveals the verifier logic.                                                                                                         | Give the business goal and necessary constraints, not every internal step.                              |
| Artificial personas                       | "You are a finance manager" often feels decorative and fake.                                                                                                                                   | Use realistic context only when it changes the work product.                                            |
| Excessive "must / only / exactly" wording | It makes the prompt adversarial and machine-generated.                                                                                                                                         | Reserve strict wording for filenames, save locations, and essential constraints.                        |
| Exact section-title checklists            | It reduces realism and can overfit the output to a template.                                                                                                                                   | Ask for the content that needs to be covered, and specify structure only when professionally necessary. |
| Robotic file references                   | Phrases like "extract data from file A and file B" can feel unnatural.                                                                                                                         | Refer to the attached workbook, report, deck, image, or dataset in context.                             |
| Putting the answer in the prompt          | If the prompt states the values, the conclusion, or the exact sentences the deliverable is scored on, the agent can copy them straight into its output and earn credit without doing the work. | Give the task, context, and constraints. Let the agent derive the graded content from the input files.  |




#### D. Add meaningful GUI interaction

GUI interaction is a critical part of this project. Many prompts can be solved entirely through code or command-line tools, especially spreadsheet, document, and presentation tasks. A strong Orangutan prompt should include work that benefits from actually opening the file, viewing the rendered output, navigating a browser, adjusting visual layout, or using an application interface.

**Core principle**

Do not add GUI interaction just for the sake of clicking. Add it when the UI changes what the agent can observe or do: rendered layout, visual overlap, page breaks, chart positioning, animations, comments, tracked changes, browser navigation, image alignment, or app-specific formatting behavior.


| GUI pattern                  | Why it works                                                                                                                                                          | Prompt language you can adapt                                                                                              |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Rendered layout checks       | The agent has to visually inspect the opened file because scripts often cannot reliably determine whether text overlaps, fits, or looks professional after rendering. |                                                                                                                            |
| Print/page setup             | Spreadsheet and document print settings are often easier and more reliable to verify through the GUI than through raw file edits.                                     | "Use page-break or print-preview view to make sure the final sheet prints cleanly on one page."                            |
| Visual reference matching    | The target is defined by appearance, spacing, proportions, or a screenshot, which pushes the agent to compare visually.                                               | "Recreate the attached reference layout as closely as possible, including spacing, relative element sizes, and placement." |
| Interactive review features  | Comments, tracked changes, animation previews, and slideshow playback are inherently UI-oriented.                                                                     | "Review the inline comments and tracked changes, then accept the approved edits and resolve the comments."                 |
| Browser navigation           | Chrome tasks require the agent to move through a website, identify a stable historical/static value, and bring it into the deliverable.                               | "Navigate to the specified public page and add the listed historical note to the report."                                  |
| Iterative visual calibration | Some visual decisions require observation and adjustment rather than a single formula.                                                                                | "Adjust the opacity/axis bounds/label position until the result is readable and visually balanced."                        |


**Bad GUI addition**

> "Open the file and click around before saving."
>
> This does not add meaningful difficulty and is not tied to the deliverable.

**Good GUI addition**

> "Open the presentation and adjust the translated German text so it fits cleanly in the existing text box without overlapping the chart. Preview the slide before saving."
>
> This is meaningful because the agent has to inspect the rendered slide and correct a visual layout problem.

**PowerPoint-specific note**

Strong presentation tasks often involve visual reasoning, not just content editing. Good examples include checking that a footnote fits inside a defined footer zone, fixing overlapping semi-transparent shapes, matching a screenshot or mockup, adjusting a gradient by visual comparison, or previewing animation timing in slideshow mode.


| Use this GUI strategy when...                                                                                                                                            | Avoid it when...                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| The task's success depends on visual rendering, layout, interactivity, browser navigation, comments, animations, or app-specific behavior.                               | The GUI step is unrelated to the deliverable or could be removed without changing the task outcome.                     |
| The GUI requirement makes the task more realistic for the profession, such as reviewing a slide deck, preparing a print-ready workbook, or editing a marked-up document. | The prompt merely says to open a file, click, or view something without requiring an observable correction or decision. |
| The expected result can still be reflected in the GTF file and rubric.                                                                                                   | The GUI action cannot be verified in the output artifact or through the task's evaluator.                               |




#### E. Tasks using Blender App

If the prompt requires work done in the Blender app, please design the task with a `.blend` output file instead of asking for screenshots of the 3D structure in a pdf, docx, etc.

You may want to include a `.blend` input file and ask the agent to make modifications to the input file and provide the resulting `.blend` file as an output.

**Prompt rewrite examples: making GUI interaction meaningful**


| Weak / artificial                                                     | Stronger / natural                                                                                                                                                                                                          |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "Use the attached PowerPoint to create exactly 5 slides and save it." | "Use the attached PowerPoint to create a 5-slide client update. On the timeline slide, adjust the callouts so none overlap when viewed in slideshow mode, then save the final deck as `client_update.pptx` on the Desktop." |
| "Create a chart from the data."                                       | "Create a chart from the data, place the legend on the left, and resize the plot area so the longest label remains readable in the spreadsheet view."                                                                       |
| "Summarize this document."                                            | "Review the marked-up document, resolve the comments that request wording changes, accept the approved tracked edits, and save a clean final copy as `policy_summary.docx` on the Desktop."                                 |




### 2.4 Validate and Finalize the Prompt

After creating/editing the prompt, confirm that the task is safe, feasible, and internally consistent. A clean prompt is not enough if the GTF files, rubrics, or verifier still reflect the old version of the task.

#### A. PII and safety check

Personally Identifiable Information must not appear anywhere in the task. Check the prompt, starting files, GTF files, rubrics, and other task content.


| PII type                         | Examples                                                                          |
| -------------------------------- | --------------------------------------------------------------------------------- |
| Real non-famous people           | Names of private individuals that can be verified online.                         |
| Contact information              | Full addresses, phone numbers, email addresses, or similar personal identifiers.  |
| Financial information            | Banking details, account numbers, payment information, or similar sensitive data. |
| Other sensitive personal details | Any private personal data that is unnecessary for the task.                       |


> **PII rule**
>
> If PII appears in the prompt, rubric, or GTF files, remove or generalize it.



#### B. Final prompt checklist

Before moving on, read the final prompt aloud and confirm the following:

☐ The prompt sounds like a realistic workplace request.
☐ The prompt is clear enough so anyone reading the prompt and the initial files can replicate the GTF without having to guess things.
☐ The exact output filename or filenames are stated clearly.
☐ The prompt says that all output files must be saved on the Desktop.
☐ The task can be completed in the VM using only installed software (LibreOffice, Chrome, standard tools) and the provided files — no unavailable applications.
☐ There is only one reasonable interpretation of the request.
☐ The prompt does not contain PII.
☐ The GUI interaction, if included, is meaningful and connected to the deliverable.
☐ The GTF files match the final version of the prompt.
☐ The rubrics evaluate the final version of the prompt.
☐ The verifier checks the correct GTF files.

### Quick Reference: Prompt Editing Decision Flow


| Question                                                                   | If yes                     | If no                                                                              |
| -------------------------------------------------------------------------- | -------------------------- | ---------------------------------------------------------------------------------- |
| Does the task match the assigned domain?                                   | Continue.                  | Skip the task if it is not in your domain.                                         |
| Are the source files usable, stable, supported, and PII-free?              | Continue.                  | Replace the input files.                                                           |
| Is the prompt clear, natural, and complex enough?                          | Keep or lightly polish it. | Rewrite the prompt.                                                                |
| Does the prompt include the exact GTF filenames and Desktop save location? | Continue.                  | Add those details naturally.                                                       |
| Does the prompt include meaningful GUI interaction where appropriate?      | Continue.                  | Add a realistic GUI requirement if it strengthens the task and remains verifiable. |
| Does the GTF file satisfy the final prompt?                                | Continue.                  | Update the GTF file.                                                               |
| Do the rubrics and verifier match the final prompt and GTF file?           | Submit after final checks. | Update them before submitting.                                                     |

### 5.1 Overview

After you have the GTF files created in the VM and uploaded to the Asset Section, come back to create the Rubrics. A rubric is a **checklist of criteria** that defines an ideal response to a user prompt.

Well-written rubrics are important because **they are used to evaluate model responses.** A judge, that is, another human or an LLM, will check your rubric criteria against a model response and assess, criterion by criterion, if the response matches those criteria.

You can think of a rubric as follows:

- A **complete**, **non-redundant**, and **accurate** set of **atomic** truth conditions specifying under which conditions a response to a given prompt is a perfect response. Basically, a **blueprint** for a perfect response to the prompt you wrote.
- Each criterion is an item on the rubric that defines a single, discrete condition needed for the ideal response.
- The LLM grader will **NOT** have access to the prompt and input files. The rubric must be written in a way that only references the GTF files and the agent response.
- You must produce weighted criteria that a judge model can use to score the agent's output against the GT.

The important shift: the GTF file is the scoring anchor. The rubric should tell the judge what dimensions to compare, not restate the answer key or reward superficial presence.

**Important note:** Start from the prompt, not the gold file. Before writing or editing any criteria, list every discrete requirement in the prompt — each deliverable, each piece of content, each constraint, each formatting or structural ask. Write one criterion per requirement. Then mark each requirement as either:

- **Anchored** — there is one correct answer, so the criterion compares against the expected file; or
- **Open** — the prompt allows multiple valid interpretations (implicit requests, open-ended recommendations, "choose an appropriate X"), so the criterion does not anchor to the expected file.

Building the rubric by describing the gold file you produced is the most common source of failure: it leaves prompt requirements uncovered (nothing checks them) and over-anchors open-ended elements to your one specific choice (penalizing other valid outputs). Walking the prompt first prevents both.

**NEW: Copilot**

The rubric section now contains copilot checks that work better than linters that provide guidelines on what is missing or wrong in your rubric and fulfilling that should result in a good rubric. The main points covered by copilot are, coverage, categorization, overfitting, framing, accuracy and atomicity. Be sure that you read the feedback provided by copilot to ensure your task has a good chance of getting a good score in the review layer

#### Rubric coverage and Length

There should be **10-30 rubric items** in total

#### Rubric Must Always Be:

**Atomic:**

The idea is for each criterion to evaluate only one element in the output files and one categorization of this. An element should be considered a major segment or item in an output file. This can be the contents of a section, a table, a chart, an image, etc. For example, if there is a table that includes multiple items, there only needs to be one criteria that evaluates the correctness of the whole table. There can also be another criteria that evaluates the visual component of the table.

Each rubric criterion should test one element in one category (visual, correctness, format gate).

Bad:

- "Table 1 in US_report.pdf and Table 2 in UK_reports.pdf are semantically equivalent to the corresponding tables in the corresponding expected files"
- "The data in Table 1 in US_Reports.pdf is semantically equivalent to the data in Table 1 of the corresponding expected File and is also similar in layout."

Good:

- "Table 1 in US_report.pdf is semantically equivalent to the corresponding table in the corresponding expected file."
- "Table 1 in US_report.pdf contains the equivalent GDP values, HDI values, and GDP per capita values to the corresponding table in the corresponding expected file."

**Self-Contained:**

The evaluator must not be required to retrieve extra content to assess the criterion besides the content of the GTF or the prompt. So you must phrase your criteria in such a way that the item can be graded without any external info. The information can also be included in the input file, whether it is order, a specific number or some layout

❌ "States the correct dosage of ibuprofen."
❌ "States the dosage to be twice the dosage mentioned in `starting file A`"
✅ "The `Experiment_Results.docx` states the same value of ibuprofen mentioned in the corresponding expected file"

- Note: `Experiment_Results.docx` = the file that the agent creates; expected file = the Ground Truth files (GTF files) that the attempter provides in the asset section

**Written with Positive Wording:**

Unless the prompt explicitly asks to omit something, the rubric items should always be written in terms of an element being present.

❌ "Fails to create a column named "Sale Prices.""
✅ "The 'Experimental Results' table in the `Experiment_Results.docx` creates a column named 'Sale Prices'."

Always start with the simple present tense (e.g., Shows the…, includes a…, provides a…, displays X as…, etc.)

✅ "`Experiment_Results.docx` states the same value of ibuprofen mentioned in the corresponding expected file."
❌ "The response must state the same value of ibuprofen mentioned in the expected file."

**Objective, Verifiable & Factually Correct:** Target values and claims that can be fact-checked.

**Comprehensive:** Includes 100% of the essential criteria.

**Relevant:** No unnecessary items.

**Formatting:** When citing variables, file names, formulas, or column/row names, enclose the items in simple backticks for better formatting.

**Specificity:** Criteria should state precisely what is expected. They should be binary (true or false). Avoid vague descriptions (e.g., "the response must be accurate"): provide more detail to make the criteria as objectively gradable as possible.

**GT-anchored:** every accuracy-based criterion must be evaluable by comparing the agent output against the reference artifact or input files.

⚠️ **Visual Criteria are on a case-by-case basis:** if there are multiple correct interpretations of the prompt request, it shouldn't be anchored to the GTF (expected file); If there is only 1 correct presentation/interpretation of the request, it should be anchored to the GTF (expected file).

Implicit requests, or situations where there can be multiple correct interpretations of visual elements, do not need to anchor to the GTF (expected file) because doing so will penalize the agent output for a different but equally correct output. Avoid having an overly restrictive rubric.

⚠️ **Cross file consistency checks do not need to be GT-anchored.** Note that they don't always belong to the correctness category.

- **Example 1:** Prompt: "The Report.pdf should have the same performance metrics table as the metrics.pdf"
  - Rubric: "Report.pdf contains the same performance metrics table with the same metric columns and values as the table shown in metrics.pdf" - Correctness
- **Example 2:** Prompt: "Pick a light blue color for the background of Metrics.pptx and use the same color in Report.pptx"
  - Rubric: "Report.pptx uses the same background color as the background color in Metrics.pptx" - Visual
- **Example 3:** Prompt "Write up a summary of the [XYZ] findings in file.docx, and then create a print-ready pdf of the docx, named poster.pdf"
  - Rubric: "poster.pdf presents semantically equivalent findings as the findings reported in file.docx" - correctness (cross file consistency checking if the pdf has the same findings as the docx);
- **Example 4:** Prompt "Group the complaints into appropriate themes in complaints.csv. Make one summary slide per theme in themes.pptx, include complaint examples for each."
  - Rubric: "Each complaint example shown on a theme slide in themes.pptx is assigned to that same theme in complaints.csv." - correctness

**Correctness-focused:** the majority of the score should test the substance of the deliverable, not whether a file or section exists.

**Tolerance-aware:** allow appropriate numeric rounding, semantic equivalence in prose, and visually comparable layouts.

**Exhaustive where outputs are enumerable:** cover all countable entries in the GT, not a small spot-check.

**Consistency-aware:** verify that repeated KPIs, charts, tables, and narrative claims agree across files and pages.

**Non-duplicative:** score each factual claim or output dimension once.

#### Additional Weight Guidance

**Weighting rule:** Weights should reflect the importance of a correct deliverable, not how often models fail. Never give a trivial gate the same weight as a core analytical result.

Based on the criteria, make sure that your weights are proportionate to the weights given to other criteria in that scoring area

- **Critical:** These are the core criteria that determine if the agent successfully completed the task. These should generally have the highest weight.
- **Important:** Important but secondary criteria in evaluating the usefulness/accuracy of the agent response.
- **Minor:** These are criteria that should be correct but have only a minor impact on the usefulness of the agent response. These should have the least weight.

**'total weight = 100' is NOT a requirement.**

- You may add/delete criteria and/or adjust the weights as long as the weight share (%) matches the guidelines stated in section 5.2 Scoring Model.



### 5.3 Write Criteria Against the Reference

A good criterion names the dimension to compare and points the judge to the GT artifact. It should not expose a long list of answer values unless those values are explicitly optional.


| Instead of writing...       | Write this way...                                                                                                                                 | Why                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Cell B4 equals $83.3B.      | The revenue figures in the summary table of `Financial_Report.docx` are semantically equivalent to the values in the corresponding expected file. | The judge can compare the expected file; the rubric should avoid answer leakage. |

### 5.4 Tolerance Rules

Criteria should be strict about correctness while allowing reasonable variation. State the acceptable comparison mode whenever the prompt permits more than one valid expression.


| Output type        | Recommended tolerance                                                                    | Example criterion language                                                                                      |
| ------------------ | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Numeric values     | Use a domain-appropriate tolerance such as +/-1%, +/-3%, +/-5%, to account for rounding. | Computed totals and intermediate values match the expected file within the specified tolerance.                 |
| Text and prose     | Use semantic equivalence unless exact wording is required.                               | The recommendation conveys the same conclusion and rationale as the expected file, even if phrased differently. |
| Open-ended methods | Allow defensible alternatives when the prompt does not prescribe one method.             | The agent's method produces results aligned with the expected file and is justified by the task constraints.    |




### 5.5 What Not To Do

- Do not hard-code literal expected values in criterion titles ("Shows X as 3.89°").
  - Instead: Compared to expected via tolerance.
- Do not write existence-only correctness criteria ("Includes a revenue analysis section").
  - Require substantive correctness against the expected.
- Do not give heavy weight to trivial checks (file extension, page count).
- Do not spot-check 7 of 44 enumerable items when you can require all 44.
- Do not penalize valid alternative phrasings, rounding within tolerance, or defensible methodological choices the prompt did not constrain.
- Do not assign all criteria MUST-PASS. MUST-PASS is reserved for format-gate criteria. Everything else is REGULAR.
- Do not assign any criterion a weight above 50 or below 1. Stay strictly in the integer range [1, 50].
- Do not write formatting or visual criteria that a degenerate solution can satisfy. Pair any "fits / no overflow / no overlap" check with a legibility guard.
  - ❌ "Text in the footer does not overflow the box." (passable by shrinking text to unreadable size)
  - ✅ "The footer text in deck.pptx fits within the footer zone and remains legible at normal zoom."
- Do not write more than three existence-only criteria per rubric. An existence-only criterion checks that something is merely present (a header, page numbers, a section, a title) without checking that its content is correct. These are weak — they reward superficial presence — so cap them at three and make every other criterion test substance.
  - ❌ "Includes a header," "Includes page numbers," "Includes a classification mark," "Includes headings" (four existence-only criteria)
  - ✅ Keep at most three such checks; convert the rest into content-correctness criteria (e.g. "The header states the correct document title and date matching the expected file")
- Do not write value criteria that only check whether a value appears in the file. Bind each value to its correct row, column, or label, so a response can't pass by dumping every candidate value.
  - ❌ "The net revenue figure appears in summary.xlsx."
  - ✅ "The net revenue figure in the Q3 row of the summary table in summary.xlsx is semantically equivalent to the corresponding expected file." (This is distinct from atomicity: a criterion can test one value (atomic) yet still fail to bind it to a location, letting a value-dump pass.)



### 5.5 Copilot checks

*(Note: source document numbers this section 5.5, duplicating the previous section number)*

Recently a new included copilot checks in task to help with quality and make the tasks easier to be completed.

**What is copilot?**

Copilot is a set of LLM-based, in-task quality checks, the revamped version of linters

Each check is configured with:

- An evaluator agent + a requirement/definition (the rules the agent judges against)
- A set of selected steps and data fields it reads from the task.

When you work the step the check is attached to, the agent runs and returns guidance in the Copilot panel rather than a simple pass/fail string.

**Where has copilot been implemented?**

*NOTE: All of the descriptions and specifics have already been detailed in the previous sections, this is just an explanation of the copilot checks*

1. **Prompt quality:** This will check if a prompt is realistic, complex, feasible, verifiable and has meaningful GUI included in it.
2. **GTF:** This will confirm if the generated GTF fulfills the prompt request without missing anything. It enumerates every discrete ask in the prompt and for each, it will provide a result of MET, MISSING, or UNVERIFIABLE depending on the GTF content.
3. **Weight protocol:** It will confirm the individual weight of each criteria and the weight share of each category
4. **Overfitting:** This will confirm if any criterion is overfit. Remember that a criterion is overfit only when its wording imposes a concrete, unjustified constraint that would reject a materially different but prompt-compliant solution.
5. **Coverage:** This evaluates that all the requirements from the prompt are included in the rubric, this helps determine whether the rubric would prevent a clearly wrong response from passing on every explicit requirement that matters to the task's intended outcome
6. **Categorization:** Analyzes if every criterion used in the rubric is correctly categorized. Ignore weights.
7. **Rubric:** Evaluates every other single aspect of the rubric mentioned in this document that has not been already evaluated by the previous checks.
8. **Accuracy:** Checks every criterion for objective factual or logical accuracy.
9. **Verifier:** Checks that the verifier and initializer are configured correctly and have the correct data format

These checks are still a work in progress and we will continue to improve them on a recurrent basis, they have been enabled because they already flag most of the errors, there will be times where they overflag, but the amount of times that that happens is low. Please be sure to not dismiss the flags and read through them before continuing your workflow.
